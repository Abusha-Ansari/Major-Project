Data Boundaries
What is transmitted vs. what stays local?
A strict boundary separates patient health information (PHI) from the numerical weights shared for learning.
Data Type Location Transmitted? Notes
Patient X-ray images Hospital disk Never Leaves Remain exclusively within hospital storage
Patient identifiers Hospital EMR Never Leaves Not involved in model training at all
Diagnostic labels Hospital disk Never Leaves Used only to supervise local training
Model weight tensors Hospital → Server Shared (Weights) Floating-point numbers, not images
Sample count Hospital → Server Shared (Count) Integer — used for FedAvg weighting
Aggregated global model Server → All Hospitals Distributed Averaged across all hospitals; contains no single hospital's raw data
Hospital auth token Hospital → Server Shared (Token) UUID for identity verification, not linked to patient records
Privacy Properties
Security guarantees in this system
🏠
Data Locality
Training data never moves. Each hospital trains exclusively on its own imaging data. The server only ever receives gradient-derived weight tensors — never pixels.
🔑
Token-Based Authentication
Each hospital registers with a unique UUID token. Weight submissions are rejected without a valid Bearer token, preventing unauthorized model poisoning.
🧮
Federated Averaging (FedAvg)
The aggregation algorithm computes a weighted average of all hospital weights. Individual hospital contributions are mathematically blended — no single hospital's training signal can be trivially isolated from the aggregate.
🛡️
Duplicate Submission Prevention
Each hospital can submit only once per federated round. The server tracks submissions in round_state.json and returns HTTP 409 on duplicate attempts.
📊
Aggregated Metrics Only
Post-round evaluation metrics (accuracy, loss, F1) are computed on a centrally held test split. No hospital-specific performance data is exposed to other participants.
🚫
No Centralized Data Collection
Unlike traditional cloud ML, there is no step where patient images are uploaded to any external server, cloud storage, or third-party API.
Training Lifecycle
Round-by-round privacy walkthrough
🌐
Global Model Distributed
The server publishes the current global model weights via GET /fl/model. All participating hospitals download the same starting checkpoint.
🔒
Local Training (Fully Private)
Each hospital trains the model on its own NORMAL/PNEUMONIA images for N epochs. This entire process happens inside the hospital's own hardware. No network traffic occurs during training.
⚖️
Weight Upload (Authenticated)
The hospital submits only the trained weight tensor file (.pt) along with its sample count and Bearer token via POST /fl/submit-update. The token is validated server-side before the upload is accepted.
🧮
FedAvg Aggregation
The admin triggers aggregation. The server computes a sample-count-weighted average of all submitted weight tensors. The result is a new global model that has learned from every hospital's data without seeing any single pixel.
🗑️
Updates Cleared
After aggregation, all individual hospital weight files are deleted from the server (when clear_updates=true). Only the averaged global model is retained. Round submission records are also cleared.
📊
Evaluation on Held-Out Test Set
The new global model is evaluated on a separate held-out test set (configured in config.py → TEST_DIR). Results (accuracy, F1, confusion matrix) are stored in evaluation_report.json and displayed in the admin dashboard.
Future Work
Differential Privacy Roadmap
The current system provides data locality as its primary privacy guarantee. A stronger formal guarantee — Differential Privacy (DP) — can be layered on top through Gaussian noise injection on gradients before submission.
🔬

Planned: DP-SGD Integration

Formal (ε, δ)-differential privacy for federated weight updates

Step 1
Per-sample Gradient Clipping
Clip each sample's gradient norm to a fixed bound C before accumulating. Prevents any single image from dominating the weight update.
Step 2
Gaussian Noise Addition
Add calibrated Gaussian noise σ · 𝒩(0, I) to the clipped gradient sum. Noise magnitude is proportional to C/batch_size and privacy budget ε.
Step 3
Privacy Budget (ε) Accounting
Track cumulative privacy expenditure across training rounds using Rényi Differential Privacy (RDP) accountant (via Opacus library).
Step 4
Server-side Verification
Optionally verify that each hospital's submitted update was produced with noise consistent with the agreed ε budget via cryptographic proof or audit log.
Recommended library: PyTorch Opacus ↗ — A PyTorch-native DP-SGD implementation with automatic RDP accounting, gradient clipping hooks, and Rényi Differential Privacy analysis tools. Drop-in replacement for standard Adam/SGD optimizers.
Honest Assessment
Current Limitations
⚠️
No Formal DP Guarantee
The current system provides data locality but not formal differential privacy. Gradient-based model inversion attacks remain theoretically possible without noise injection.
⚠️
Plain-text Password Storage
Hospital passwords are stored as plain text in hospitals.json. Production deployment should hash passwords with bcrypt or Argon2.
⚠️
No TLS Encryption
The server runs over plain HTTP. In production, all endpoints must be served over HTTPS with a valid TLS certificate to protect weights in transit.
⚠️
File-based State
Hospital registry and round state are stored in JSON files. A production system should use a proper database with access controls and audit logging.
